# A4: Secrets Management & Cryptography

This backend implementation successfully fulfills the requirements for the **A4** grading criteria:

### 1. No Secrets Committed to the Repo
- **Implementation:** We enforce a strict separation of code and configuration. 
- **Demonstration:** Checking the `.gitignore` file reveals that `.env` is explicitly ignored. Reviewing the Git history or running a `grep` across the codebase will yield no hardcoded API keys, JWT secrets, or database credentials.

### 2. Secrets Injected via Environment Variables
- **Implementation:** Secrets are loaded safely at runtime using the `dotenv` package.
- **Demonstration:** In `server.js`, `dotenv.config()` is called at the very top. Throughout the application, secrets are referenced by their variable names (e.g., `process.env.JWT_SECRET` in `auth.controller.js`), never by their actual values.

### 3. TLS/HTTPS for Data in Transit
- **Implementation:** The backend explicitly runs over an encrypted HTTPS connection to prevent man-in-the-middle packet sniffing.
- **Demonstration:** In `server.js`, we use the native Node `https` module to bind the Express application. The server boots using SSL certificates (`server.key` and `server.cert` generated by `node-forge`) so that traffic to `https://localhost:5000` is encrypted.

### 4. Sensitive Data Hashed (Vetted Algorithm)
- **Implementation:** We do not roll our own crypto. We use `bcryptjs`, a vetted and industry-standard slow-adaptive hashing library.
- **Demonstration:** (Cross-referenced with A2) `bcrypt.hash(password, 10)` is used to securely encrypt user passwords before they are stored in the database.
