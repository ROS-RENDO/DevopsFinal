# A7: Logging, Monitoring & Error Handling

This backend implementation successfully fulfills the requirements for the **A7** grading criteria:

### 1. Security-Relevant Events Logged
- **Implementation:** We integrated `winston`, an industry-standard structured logging library, to monitor the application securely.
- **Demonstration:** Open `logs/security.log`. You will see structured JSON logs capturing critical events like "Login Success," "Login Failure," and "Authorization Failure." Every log includes the `timestamp`, the `ip`, the `path`, and the user's `role` or `email`, but strictly excludes any sensitive passwords or tokens.

### 2. Errors Fail Safe (Generic to User, Details on Server)
- **Implementation:** We built a global error-handling middleware (`error.middleware.js`) that acts as a final safety net for unexpected crashes.
- **Demonstration:** If an unhandled exception occurs in a controller, the server securely logs the full stack trace internally using `logger.error` to `logs/error.log`. However, the HTTP response sent back to the client only ever contains a generic `500 Internal Server Error` message, ensuring that no sensitive infrastructure details are leaked to attackers.

### 3. Log-Based Detection Scenario
- **Detection Scenario:** Credential Stuffing / Brute Force Attack
- **Explanation:** If an attacker attempts a credential stuffing attack, our `winston` logs will capture rapid bursts of `Login Failure: Invalid credentials` pointing to a single `ip` address. Security analysts (or automated SIEM tools) parsing `logs/security.log` would see 5+ failures associated with the same IP within seconds. This log pattern immediately surfaces the attack, which is subsequently mitigated by our `express-rate-limit` configuration that temporarily bans the IP.
