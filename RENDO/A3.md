# A3: Input Validation & Injection Defense

This backend implementation successfully fulfills the requirements for the **A3** grading criteria (Input Validation & Injection Defense):

### 1. Server-side Allow-List Validation
- **Implementation:** The backend does not trust any client input. It uses the `zod` library to perform strict schema validation on all incoming request bodies before they reach the controllers.
- **Demonstration:** In `src/validations/auth.validation.js`, schemas define the exact format expected (e.g., email format, minimum password length, and restricted characters for names). Sending a request with an invalid email or a password that is too short results in an immediate `400 Bad Request` with a detailed error array.

### 2. Parameterized Queries / ORM (SQL Injection Fails)
- **Implementation:** The application uses Prisma ORM to interact with the SQLite database. Prisma automatically generates prepared statements and uses parameterized queries for all database operations.
- **Demonstration:** Attempting to inject a SQL payload into the login form (e.g., `"email": "admin@test.com' OR 1=1 --"`) fails completely. The ORM treats the entire string as a literal value, preventing it from altering the query structure. The server responds with `400 Bad Request` for "Invalid credentials".

### 3. Output Encoding / Escaping (XSS Prevention)
- **Implementation:** We intercept all requests using a generic validation middleware (`src/middleware/validate.middleware.js`). After passing the `zod` schema, all string fields are passed through the `xss` package to aggressively strip out malicious HTML and script tags.
- **Demonstration:** Registering a user with a malicious payload like `"name": "<script>alert('Hacked')</script>Rendo"` is completely neutralized. The `zod` validation explicitly rejects `<` and `>` characters with a regex, completely blocking the attack. If it were allowed through, the `xss` sanitizer would encode it, ensuring any downstream consumers render it safely as text, not script.
